# Bank Receipt Clearing – How It Works

This document explains three things:

1. **How clearing works:** what happens to the invoice in SAP.
2. **What the ABAP does in SAP** (`Z_BANK_POST_CLEAR`).
3. **How `active_bt3i` and `active_bs` are updated** after posting.

It ends with a walkthrough of a real run (document 1900000004).

For setup, payloads and how to call the API, see [BANK_POSTING_PROCESS.md](BANK_POSTING_PROCESS.md).

---

## 1. End-to-end flow

```
 ┌───────────────────────┐
 │ Request               │  items[] or Excel file
 │ (invoice + bank data) │  invoice_ref, customer, amount, utr, bank_gl ...
 └──────────┬────────────┘
            ▼
 ┌───────────────────────┐   Python  bank_posting/posting.py
 │ 1. Normalise          │   dates, amounts, ALPHA (30000001 → 0030000001)
 │ 2. Validate           │   mandatory fields, Dr = Cr, duplicates
 │ 3. Open-item check    │──► SAP BSID (read via ZGENERIC_DATA_SRV)
 │    amount & currency  │    invoice must be open, amount must match
 └──────────┬────────────┘
            │ dry_run = false
            ▼
 ┌───────────────────────┐   SAP  Z_BANK_POST_CLEAR  (via /sap/bc/soap/rfc)
 │ 4. Post + clear       │   Dr Bank G/L / Cr Customer, invoice cleared
 │ 5. Confirm clearing   │   read BSAD → clearing document
 └──────────┬────────────┘
            │ document_no
            ▼
 ┌───────────────────────┐   Python  bank_posting/document_link.py
 │ 6. DB write-back      │   active_bt3i.documentid / active_bs.documentid
 └──────────┬────────────┘
            ▼
       JSON response
```

## 2. How clearing works (accounting)

### 2.1 Before the bank receipt

The customer invoice is an **open item**. SAP stores open customer items in
`BSID` (`BSID_VIEW` in S/4HANA).

| Table | Company | Customer | Doc | Dr/Cr | Amount | Clearing doc |
|---|---|---|---|---|---|---|
| BSID (open) | DAT1 | 0030000001 | 1800000001 | Dr (S) | 10,000 | – |

### 2.2 Posting with clearing

One SAP document is created, using incoming-payment logic (same as F-28 / FB05):

| Line | Posting key | Account | Dr/Cr | Amount |
|---|---|---|---|---|
| 1 | 40 | Bank G/L 24500000 | Dr | 10,000 |
| 2 | 15 (generated by clearing) | Customer 0030000001 | Cr | 10,000 |

At the same time, SAP **links** the new customer credit line (line 2) with the open invoice:

- The invoice and the payment line both get `AUGBL` (clearing document) = the new document number, and `AUGDT` (clearing date) = the posting date.
- Both lines move from **BSID (open)** to **BSAD (cleared)**.
- The customer balance for this invoice becomes zero.

### 2.3 After the bank receipt

| Table | Doc | Dr/Cr | Amount | AUGBL | AUGDT |
|---|---|---|---|---|---|
| BSAD (cleared) | 1800000001 (invoice) | Dr | 10,000 | 1900000004 | 2026-11-13 |
| BSAD (cleared) | 1900000004 (payment) | Cr | 10,000 | 1900000004 | 2026-11-13 |
| BSIS (G/L) | 1900000004 (bank line) | Dr | 10,000 | – | – |

**Posting document = clearing document.** In F-30 / FB05 the document that posts the payment is the same document that clears the invoice. That is why the API returns the same number in both `document_no` and `clearing_doc`.

### 2.4 When clearing is not possible

The API only posts when the bank amount **equals** the open amount. Other cases are rejected before SAP is called:

| Case | Result |
|---|---|
| Invoice not open (already cleared / wrong reference) | `INVALID: No open item in SAP ...` |
| Bank amount ≠ open amount | `INVALID: Amount mismatch ...` |
| Different currency | `INVALID: Currency mismatch ...` |

Partial payments, residual items and write-offs of differences (bank charges, TDS) are **not supported yet**.

## 3. What the ABAP does in SAP

| Object | Value |
|---|---|
| Function module | `Z_BANK_POST_CLEAR` (RFC-enabled) |
| Function group | `ZBANK_POST` |
| Package | `$TMP` (local, not transported) |
| System | S/4HANA 2023, SID A4H, client 200 |
| Called by | Python over SOAP-RFC `/sap/bc/soap/rfc` |
| Source | [sap_abap/Z_BANK_POST_CLEAR.abap](sap_abap/Z_BANK_POST_CLEAR.abap) |

### 3.1 Interface

| Import | Example (real run) | Meaning |
|---|---|---|
| IV_BUKRS | DAT1 | Company code |
| IV_KUNNR | 30000001 | Customer (converted to 0030000001) |
| IV_BLDAT / IV_BUDAT | 2026-11-13 | Document / posting date |
| IV_BLART | DZ | Document type (customer payment) |
| IV_WAERS | INR | Currency |
| IV_HKONT | 24500000 | Bank G/L account |
| IV_WRBTR | 10000.00 | Amount |
| IV_MATCH_BY | BELNR | Field used to find the invoice: `XBLNR` / `ZUONR` / `BELNR` |
| IV_INVOICE_REF | 1800000001 | Value of that field |
| IV_UTR | FHDFCH01086920901 | Bank reference (UTR) |
| IV_SGTXT | WPP MEDIA receipt ... | Line item text |
| IV_VALUT, IV_MONAT | (empty) | Optional |

| Export | Example | Meaning |
|---|---|---|
| EV_STATUS | S | `S` posted and cleared, `W` posted but clearing not found, `E` error (nothing posted) |
| EV_BELNR / EV_GJAHR | 1900000004 / 2026 | Posted document |
| EV_AUGBL / EV_AUGDT | 1900000004 / 2026-11-13 | Clearing document / date |
| EV_MESSAGE | Document 1900000004 posted and cleared BELNR 1800000001 | Text |

### 3.2 Step by step

**Step 0. Normalise keys.**
`CONVERSION_EXIT_ALPHA_INPUT` pads the customer to 10 digits. When `MATCH_BY = BELNR`, the invoice number is also padded to the 10-character `BELNR_D`.

**Step 1. Duplicate check (only if a UTR is given).**
```abap
SELECT SINGLE belnr FROM bkpf
  WHERE bukrs = iv_bukrs AND blart = iv_blart
    AND xblnr = iv_utr   AND stblg = space.     " not reversed
```
If a document is found, the FM returns `E "UTR ... already posted in document ..."` and stops.

**Step 2. Open-item check.**
```abap
SELECT COUNT(*) FROM bsid_view
  WHERE bukrs = iv_bukrs AND kunnr = lv_kunnr
    AND <xblnr | zuonr | belnr> = <invoice ref>.
```
If nothing is found, the FM returns `E "No open item for customer ..."` and stops.

**Step 3. Build the posting data.**
This is the same data a user would type into FB05. Values are converted to the user's date and number format with `WRITE ... TO`.

`FTPOST` (header `K` and bank line `P`), real run:

| STYPE | FNAM | FVAL |
|---|---|---|
| K | BKPF-BLDAT | 13.11.2026 |
| K | BKPF-BUDAT | 13.11.2026 |
| K | BKPF-BLART | DZ |
| K | BKPF-BUKRS | DAT1 |
| K | BKPF-WAERS | INR |
| K | BKPF-XBLNR | FHDFCH01086920901 (UTR, or invoice ref if no UTR) |
| P | RF05A-NEWBS | 40 |
| P | BSEG-HKONT | 24500000 |
| P | BSEG-WRBTR | 10,000.00 |
| P | BSEG-ZUONR | 1800000001 |
| P | BSEG-SGTXT | WPP MEDIA receipt FHDFCH01086920901 |

`FTCLEAR`, which tells SAP which open item to clear:

| AGKOA | AGKON | AGBUK | XNOPS | SELFD | SELVON |
|---|---|---|---|---|---|
| D (customer) | 0030000001 | DAT1 | X (normal open items) | BELNR | 1800000001 |

**Step 4. Post with clearing.**
```abap
POSTING_INTERFACE_START     i_function = 'C'   " call transaction
                            i_mode     = 'N'   " no screens
                            i_update   = 'S'   " synchronous update
POSTING_INTERFACE_CLEARING  i_auglv    = 'EINGZAHL'  " incoming payment
                            i_tcode    = 'FB05'
                            tables t_ftpost, t_ftclear, t_fttax, t_blntab
POSTING_INTERFACE_END
```
SAP runs FB05 in the background. It enters the header and the bank line, selects the open item from `FTCLEAR`, generates the customer credit line and posts. All standard FI checks apply here: period open, account valid, field status, balance = 0, authorisation.

The posted document number comes back in `T_BLNTAB`. If FB05 raises an error, the FM returns `E` with SAP's message text (for example `Field BSEG-VALUT does not exist in dynpro SAPMF05A 0300`).

**Step 5. Confirm the clearing.**
```abap
SELECT SINGLE augbl, augdt FROM bsad_view
  WHERE bukrs = iv_bukrs AND kunnr = lv_kunnr AND augbl = ev_belnr.
```
- Found → `S` (posted and cleared)
- Not found → `W` (posted, but clearing not confirmed; check FBL5N)

### 3.3 Why this design

| Choice | Reason |
|---|---|
| `POSTING_INTERFACE_CLEARING` instead of a BDC on F-30 | No hard-coded screen sequence. No coding-block pop-up handling. Works for any G/L field status. |
| RFC + SOAP instead of OData | Standard OData posting services are not activated ("No System Alias"), and SEGW cannot be created through the API. SOAP-RFC is built in. |
| Confirmation in `BSAD_VIEW` | "Posted" does not guarantee "cleared". This step proves the invoice is cleared. |

## 4. How `active_bt3i` and `active_bs` are updated

Code: [document_link.py](document_link.py). It runs at the end of the API call when:

- `dry_run` is `false`
- `update_db` is `true` (default)
- the row status is `SUCCESS` or `POSTED_NOT_CLEARED` (a SAP document exists)

### 4.1 Input to the write-back

For each posted row, the code builds a mapping **Assignment → DocumentNo**:

| Assignment | DocumentNo |
|---|---|
| invoice_ref (1800000001) | 1900000004 |
| utr (FHDFCH01086920901), if given | 1900000004 |

### 4.2 Candidate rows

```sql
SELECT * FROM active_bt3i WHERE transactiontype = 'Invoice' AND documentid IS NULL;
SELECT * FROM active_bs   WHERE transactiontype = 'Bank'    AND documentid IS NULL;
```

### 4.3 Matching (`connect_document_id`, same rules as the AR Inbox flow)

All keys are normalised before comparing: converted to text, trimmed, upper-cased, and a trailing `.0` removed.

| Table | Column compared with Assignment | Result |
|---|---|---|
| `active_bt3i` | `documentnumber` | `documentid` = DocumentNo |
| `active_bs` | `transactionref` | `documentid` = DocumentNo |

### 4.4 The update

Only `documentid` is changed, by primary key, and only where it is still NULL.

```sql
UPDATE public.active_bt3i AS t
SET    documentid = v.documentid
FROM  (VALUES (...)) AS v (processcode, themename, transactiontype, orgid, documentnumber, sno, documentid)
WHERE  t.processcode = v.processcode AND t.themename = v.themename
  AND  t.transactiontype = v.transactiontype AND t.orgid = v.orgid
  AND  t.documentnumber = v.documentnumber AND t.sno = v.sno
  AND  t.documentid IS NULL;

UPDATE public.active_bs AS t
SET    documentid = v.documentid
FROM  (VALUES (...)) AS v (processcode, themename, transactiontype, orgid, accountnumber, transactiondate, sno, documentid)
WHERE  <same primary-key join> AND t.documentid IS NULL;
```

Both updates run in **one database transaction**: either both commit or both roll back.
If the DB step fails after SAP has posted, the SAP document stays, and the error is returned in `db_update.error`.

### 4.5 Real run, before and after

| Table | Key | documentid before | documentid after |
|---|---|---|---|
| active_bt3i | Invoice 1800000001 / sno 1 | NULL | **1900000004** |
| active_bs | 13-11-2026 / sno 2 / FHDFCH01086920901 | NULL | **1900000004** |

### 4.6 Which rows can be updated

| `active_bt3i` rows | documentid | Updated by this API? |
|---|---|---|
| From SAP sync (`source_table = 'active_bsid'`, `grouptransactionref LIKE 'CTXSAP%'`), 52 rows | Already set to the SAP invoice BELNR | **No.** Skipped because of `IS NULL`. |
| DataTwin's own ingestion (`source_table IS NULL`), about 66 rows | NULL | Yes, if `documentnumber` = invoice_ref |

To list only the SAP invoices:

```sql
SELECT orgid, documentnumber, documentid, sendername, documentvalue, grouptransactionref
FROM   active_bt3i
WHERE  transactiontype = 'Invoice'
  AND  source_table = 'active_bsid'
  AND  grouptransactionref LIKE 'CTXSAP%';
```

## 5. Real run walkthrough (2026-11-15)

### 5.1 Data selection

- **active_bt3i:** of 67 invoices with `documentid` NULL, one matched a SAP open item by number and amount: **1800000001** (WPP MEDIA, 10,000 INR). In SAP this is DAT1 / customer 0030000001 / BELNR 1800000001.
- **active_bs:** the invoice's `linkref` = **FHDFCH01086920901**. A bank row with the same `transactionref` exists (13-11-2026, credit 40,000), so it was sent as the UTR.

Request:

```json
{
  "dry_run": false,
  "match_by": "BELNR",
  "items": [{
    "doc_date": "2026-11-13", "posting_date": "2026-11-13",
    "company_code": "DAT1", "currency": "INR",
    "customer": "30000001", "bank_gl": "24500000",
    "amount": 10000.00, "invoice_ref": "1800000001",
    "utr": "FHDFCH01086920901",
    "item_text": "WPP MEDIA receipt FHDFCH01086920901"
  }]
}
```

### 5.2 Execution

| Step | Result |
|---|---|
| Dry run | `VALID`. Open item 10,000 INR matched. |
| Live attempt 1 | `ERROR: No open item ... BELNR = 00000000001800000001`. The ABAP padded BELNR to 20 characters. The FM stopped before posting, so nothing was posted. The FM was fixed (convert into a 10-character `BELNR_D`) and re-activated through ADT. |
| Live attempt 2 | `SUCCESS`. Document **1900000004** posted and cleared BELNR 1800000001. |
| SAP check | 1800000001 is no longer in BSID (open items). |
| DB | `active_bt3i` 1 row and `active_bs` 1 row, `documentid = 1900000004`. |

### 5.3 Issue found after the run: wrong customer

| | DB (`active_bt3i`) | SAP (DAT1) |
|---|---|---|
| Doc no | 1800000001 | 1800000001 |
| Amount | 10,000 INR | 10,000 INR |
| Customer | **WPP MEDIA INDIA PRIVATE LIMITED** | **0030000001 = TEST Customer_02 TEST02** |
| Source | `source_table` NULL (DataTwin ingestion, not SAP) | – |

The match used only document number and amount. The customers are different, so this was a coincidental match. Posting 1900000004 links WPP MEDIA's bank receipt to a SAP test customer's document. The DB links written in step 4.5 are therefore also wrong.

**To undo it:**

1. SAP: run **FBRA** (reset cleared items) for document 1900000004 / DAT1 / 2026, then **FB08** (reverse).
2. DB:
   ```sql
   UPDATE active_bt3i SET documentid = NULL
    WHERE transactiontype = 'Invoice' AND documentnumber = '1800000001' AND documentid = '1900000004';
   UPDATE active_bs SET documentid = NULL
    WHERE transactionref = 'FHDFCH01086920901' AND documentid = '1900000004';
   ```

Other notes on this run:

- The bank receipt (40,000) also covers JM3304800001 and JM3304800002 (15,000 each). These are not in SAP, so only 10,000 was posted. The bank row is still marked with a `documentid`.
- The UTR FHDFCH01086920901 is now used in SAP, so the duplicate check will reject any further posting with it.

## 6. Known gaps and next steps

| # | Gap | Proposed fix |
|---|---|---|
| 1 | Matching does not check the customer, which caused the wrong posting in section 5.3 | Before posting, compare the SAP customer name (KNA1) with `sendername` and reject on mismatch |
| 2 | SAP-sourced invoices already have `documentid`, so they are never updated | Add `clearingdocid` / `clearingdate` columns to `active_bt3i` and write the clearing document there |
| 3 | `active_bt3i` has no company code | Look it up from `active_bsid` by `belnr`, or store `bukrs` during the sync |
| 4 | One bank receipt that covers several invoices | Done for connections: `POST /api/clearing/post` + `Z_BANK_POST_CLEAR_MULTI`, see [CONNECTION_CLEARING_API.md](CONNECTION_CLEARING_API.md) |
| 5 | Partial payment, bank charges, TDS | Residual items / difference posting in the FM |
| 6 | SAP objects in `$TMP` | Move them to a Z package with a transport |
