How a record moves

The SAP OData service returns whole tables only: it has no date or key filter, and WhereClause is not a property of TableDataSet. The worker therefore reads all of BSID each minute and works out the changes on the DataTwin side. Sixty rows take about 4.5 seconds.

  1. Poll SAP every 60 s

    The worker fetches BSID page by page and checks that it received as many rows as SAP's $count. If the counts differ, it still applies new and changed rows but skips the removal check for that minute.

  2. Detect new, changed and removed rows

    Each row gets a sap_key_hash from the DDIC key (MANDT, BUKRS, KUNNR, UMSKS, UMSKZ, AUGDT, AUGBL, ZUONR, GJAHR, BELNR, BUZEI) and a row_hash from its values.

    • An unknown key is inserted with a new passportid as NEW PENDING.
    • A changed hash becomes CHANGED PENDING.
    • A key missing for two polls becomes REMOVED.

  3. Queue

    The PENDING rows in active_bsid are the queue. When no ingestion run is active, the worker claims them as IN_PROGRESS and stamps them with a run id. Rows that arrive during a run wait for the next one.

  4. Stage the batch

    The claimed rows are copied to active_bsid_delta: passportid plus the columns listed in columns_bsid. The table is rebuilt for every run, so the ingestion service only ever sees the current batch.

  5. Call the ingestion API

    POST /api/ingest/table carries process_code=BT3I and transaction_type=Invoice. The service then:

    • skips AI classification;
    • maps the columns with the BT3I theme and upserts them into active_bt3i;
    • writes transaction_log;
    • shows the run on its dashboard with a live log.

  6. Close the run

    Success marks the rows DONE with ingested_at. A failure sends them back to PENDING, and they become FAILED after the third attempt. The next run starts only after this one has finished.

passportid

Every SAP record that reaches DataTwin gets one passportid the first time the poller sees it. The id never changes, even when the SAP values change or the table is re-read. The ingestion service carries it into active_bt3i, so a record can be traced from SAP to the target table.

Status values

sap_status Meaning
ACTIVE In SAP and unchanged since it was first stored.
NEW First seen by the poller.
CHANGED Values changed in SAP since it was last seen.
REMOVED Missing from BSID for two polls, usually because the item was cleared and moved to BSAD. The row is kept and is not sent to ingestion.
ingestion_status Meaning
PENDING Waiting for the next ingestion run.
IN_PROGRESS Claimed by the run in ingestion_run_id.
DONE Ingested, or already loaded before the delta sync started.
FAILED Failed three times. Re-queue it with cli.py delta-retry BSID.

Open items as SAP shows them today: WHERE sap_status <> 'REMOVED'. A changed row goes back to PENDING even if it had been DONE, so the new values are ingested as well.

Ingestion call

The call is synchronous: the service maps and upserts the batch before it answers, which took about 2½ minutes for the first BT3I batch. The client waits up to 30 minutes. If the answer is lost, it looks up the transaction_id in transaction_log and uses that status.

Request
POST /api/ingest/table
{
  "db": "dm00005",
  "table_name": "active_bsid_delta",
  "tenant_id": "DM00005",
  "org_id": "OM0000000001",
  "transaction_id": "TR_SAP_BSID_20261119000339_219469",
  "process_code": "BT3I",
  "transaction_type": "Invoice"
}
Response
{
  "success": true,
  "job_id": "TR_SAP_BSID_20261119000339_219469",
  "status": "completed",
  "data": {
    "status": "Success",
    "target_process_code": "BT3I",
    "process_code_source": "caller",
    "target_table": "active_bt3i"
  }
}

Tables

Table Role
active_bsid Copy of SAP BSID. Column types come from the SAP dictionary: amounts as double precision, NUMC as bigint, the rest as text. It also holds the control columns: passportid, sap_key_hash, row_hash, sap_status, ingestion_status, ingestion_run_id, retry_count, error_message, missing_count, first_seen_at, last_seen_at, changed_at, removed_at, ingested_at.
active_bsid_delta Staging table for the current batch, rebuilt every run.
sap_ingestion_run One row per run. run_id is the transaction_id sent to the API. A unique index allows only one RUNNING row.
sap_extraction_state Last poll per table: SAP count, rows fetched, new / changed / removed, last error.
transaction_log Written by the ingestion service per transaction id. Used when the HTTP answer is lost.
active_bt3i Target. Rows from this flow have input = table://dm00005/active_bsid_delta and carry passportid and transactionid.
active_bsid_bak_20261118_234602 The table as it was before the delta sync started.

When things fail

Situation What happens
SAP down or OData error Nothing changes in the database. The error is saved in sap_extraction_state.last_error and the next poll tries again.
Fewer rows received than SAP's $count New and changed rows are applied. The removal check waits for a complete read.
Ingestion returns a failure Rows go back to PENDING with retry_count + 1. After three attempts they are FAILED.
No answer from the ingestion API The client reads transaction_log for its transaction id. Success marks the rows done. Anything else re-queues them; the service's upsert is idempotent, so a resend does not duplicate rows.
Worker stopped during a run On the next start it finishes the RUNNING run first, then claims new rows.
Second run while one is active Refused by a file lock and the database index. The API answers 409; cron exits with code 75.
Full reload of BSID requested Refused with 400. A full reload would drop the table and its passportids.

Configuration

In config.ini of sap-extraction-api. Every key can also be set as an environment variable, for example INGESTION_BASE_URL or DELTA_TABLES.

[delta]
tables = BSID
poll_seconds = 60
missing_polls_before_removed = 2
passport_prefix = PPSAP

[ingestion]
enabled = true
base_url = http://<ingestion-host>:8050      ; must be reachable from the server
batch_size = 5000
job_timeout_minutes = 30
max_retries = 3
process_code_bsid = BT3I
transaction_type_bsid = Invoice
theme_name_bsid =                         ; empty = theme picked once, then reused
columns_bsid = bukrs, kunnr, belnr, gjahr, buzei, blart, bldat, budat, cpudt, xblnr, zuonr,
               waers, dmbtr, wrbtr, shkzg, zfbdt, zterm, zbd1t, sgtxt, xref1, xref2, xref3,
               augdt, augbl, gsber, hkont, mwskz

Keep columns_bsid short. The ingestion service adds every column it cannot map as a new column of the target table.

Running it

Command line
# one time per table
python cli.py delta-init BSID

# every 60 s: poll + ingestion
python cli.py worker

python cli.py delta-status
python cli.py delta-retry BSID

# Linux server
sudo systemctl enable --now sap-extraction-worker
API (port 8002) Does
GET /api/delta/status Counts, last poll, recent runs
POST /api/delta/poll Poll SAP now
POST /api/delta/ingest Start a run in the background
POST /api/delta/retry FAILED back to PENDING

Monitoring queries

-- what is waiting or stuck
SELECT passportid, belnr, xblnr, kunnr, dmbtr, sap_status, ingestion_status, retry_count, error_message
FROM active_bsid WHERE ingestion_status <> 'DONE' ORDER BY first_seen_at;

-- one record from SAP to BT3I
SELECT b.passportid, b.belnr, b.ingestion_run_id, r.status, t.processcode, t.themename, t.documentnumber
FROM active_bsid b
LEFT JOIN sap_ingestion_run r ON r.run_id = b.ingestion_run_id
LEFT JOIN active_bt3i t ON t.passportid = b.passportid
WHERE b.passportid = 'PPSAP0126270000059';

-- recent runs
SELECT run_id, status, record_count, started_at, finished_at, error
FROM sap_ingestion_run ORDER BY started_at DESC LIMIT 20;

Open items

  • Blocker

    Restart the ingestion service on port 8050 so it runs the new code. Then create config.ini with the [delta] and [ingestion] sections and start python cli.py worker.

  • Decide

    Theme Inv_BT3I_01 does not follow the existing SAP invoice convention. Bank clearing and the AR Inbox read senderaccount, documentvalue and documentnumber.

    • It maps KUNNR to ReceiverAccount instead of SenderAccount.
    • It maps DMBTR to AmountInLocalCurrency, so DocumentValue and BaseValue stay empty.
    • It uses BELNR as DocumentNumber, where earlier SAP rows use XBLNR.

    Correct the mapping, then pin it with theme_name_bsid.

  • Decide

    The first BT3I run added 79 unmapped SAP columns to active_bt3i, which now has 256 columns. Only the two new rows use them. They can be dropped; later runs send only columns_bsid.

  • Deploy

    On the server, base_url must point to an ingestion service the server can reach. The office LAN address used while testing is not reachable from a server.

  • Repo

    Review and commit the changes to api.py, app.py and job_manager.py in data_modelling-ingestion.

  • Tidy

    Drop active_bsid_bak_20261118_234602 once the flow has run cleanly for a while. The AI-made GLE theme GLE_LdgrEnt from the first run is still in theme_mapping.
