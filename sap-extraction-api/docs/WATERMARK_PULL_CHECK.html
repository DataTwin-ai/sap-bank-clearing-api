Watermark Pull Check

After the first full load, each 1-minute run asks SAP only for rows created or modified since the last pull. This page shows the rule SAP applies, lets you test a row against it, and lists what DataTwin does with each answer.

One run, step by step

  1. Read the watermark

    From sap_extraction_state for BSID, for example 19-11-2026 10:00:59.

  2. Subtract the overlap

    5 minutes back gives 19-11-2026 09:55:59. Documents stamped just before the last pull but committed just after it are caught this way.

  3. Ask SAP

    Z_BSID_DELTA returns only rows whose created or modified time is on or after that point, plus SAP's own clock at the start of the query.

  4. Check each returned row in DataTwin

    The key fingerprint (sap_key_hash) tells new from known. For a known row, the value fingerprint (row_hash) tells changed from unchanged.

  5. Queue what changed

    New and changed rows become PENDING and go to ingestion. Unchanged repeats are skipped.

  6. Move the watermark

    Only after everything above succeeded, set the watermark to SAP's clock from step 3. If the run fails, it stays where it was and the next run covers the gap.

Three rules that keep it safe

SAP's clock only

The watermark always comes from SAP. The DataTwin server can be in another time zone or a few seconds off, and that would make rows slip through.

Move only on success

A failed pull leaves the watermark unchanged. The next pull asks for a longer window and nothing is lost.

Repeats are harmless

The overlap returns some rows twice. Their key and value fingerprints match what is stored, so nothing is written and nothing is ingested again.
