BSID New Record Detection

SAP posts one new invoice, so BSID now has 61 open items while active_bsid has 60. The poller still reads all 61, works out which one is new, and stores and ingests only that row.

61rows read from SAP
60rows already in active_bsid

Four steps every minute

  1. Pull61

    All BSID rows come from SAP. The OData service cannot filter by date or key, so it always returns the whole table. The rows stay in memory and are not written to the database.

  2. Compare61 → 1

    Each row's key fingerprint is looked up among the 60 already stored. One is not found.

  3. Store1

    One INSERT into active_bsid with a new passportid, status NEW PENDING. The other 60 rows are left as they are.

  4. Ingest1

    Only PENDING rows are copied to active_bsid_delta, so the ingestion API reads that one row.

The fingerprint: SAP's own key

SAP defines which fields make a BSID line unique: eleven key fields, from client down to line item. The poller joins their values and hashes them into sap_key_hash. Every row in active_bsid keeps this hash, so checking "have we seen this row before?" is one lookup.

Why not compare count, document number or date?

Row count

60 → 61 says something was added, not which row. If one invoice is cleared and a new one posted in the same minute, the count stays at 60 although two things changed.

Document number alone

The same BELNR can exist in another company code or fiscal year, and one document can have several line items (BUZEI). Only the full key identifies one BSID line.

Entry date

BSID's entry date (CPUDT) has no time, so several polls a day would see the same date. The OData service cannot filter on it anyway.

Can SAP send only the new row?

Not with the current OData service. It returns whole tables, and adding a filter field needs a change in SAP Gateway. A full read of BSID takes about 4.5 seconds, so it is fine every minute.

For large tables such as BSEG or ACDOCA, add a small RFC function in SAP through ADT, the same way Z_BANK_POST_CLEAR was created. It would return only the documents entered after the last poll, using BKPF's entry date and time (CPUDT + CPUTM). The comparison above stays the same; SAP just sends fewer rows.
